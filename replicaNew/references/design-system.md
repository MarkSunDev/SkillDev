# 阶段 3：design 立形（截图驱动的 UI/UX 重构）

输入：原 App 截图（`replica/screens/`）+ spec 的页面清单。产出：`replica/design.md`
（视觉风格章程）+ `replica/design/`（tokens.json、tokens 源码、components.md、
gallery/ 验收截图）。

截图的正确用法：它是**视觉行为参照物**——看信息层级、状态、组件行为，不描像素。
和代码层"行为参照物非模板"是同一条纪律的视觉版。

三不：
- 不取原色值当新主题色（原主色要进 origin.json 的 colors 列表，sweep 会抓）；
- 不逐像素复刻构图（同 job 换布局，见 §2）；
- 不搬运资产（图标/插画/字体文件）。

## 0. design.md（视觉风格章程，先于一切 token）

一页纸写清"这个 App 长什么样、不像什么样"，是用户过目的第一个视觉交付物：

```
# {{新 App}} 视觉风格章程
场景与情绪: 一句话（例: 深夜街角的霓虹感 / 清晨咖啡馆的纸质感）
anti-reference: 长得像谁就不行——原 App + 品类头部竞品各列一条具体特征
主色与中性色族: 色相族 + 为什么不是原 App 的邻近色
形面语言: 圆角/描边/阴影的整体策略（例: 细描边平面风，不用投影）
密度与呼吸感: 间距基准（8dp）与留白原则
字阶策略: 字重对比怎么建立层级
动效: 转场与微动效的一句话语言（例: 淡入上移，不用右滑入）
插画/图标/资产: 全部新做的方向与来源
可借鉴参照: craft reference——形面/排版学哪家（可以是其它品类的好产品），
            只学手法不搬资产；没有参照就先出 2-3 个风格 tile 让用户选
资产来源: 图标/字体/插画的许可证与出处（可审计）
无障碍: 最小触控 44dp / 文字缩放 / 对比度 AA / 控件标签 / 手势的替代操作
宽屏与平板: 做还是不做；做则写明确行为
状态: proposed / approved（用户点头后改 approved；后续改动留痕）
```

章程批准后才定 token 值——先定方向再定数字，防止 token 表变成"看起来很专业的随机数"。

### 章程必须包含「组件形面规格」（不能只写圆角 token）

只写"圆角 md=16、描边 1dp"不够，模型会把它套到所有控件上，产出一屏"描边胶囊
按钮"。每个变体必须写清填充/描边/阴影：

```
按钮     primary=实底主色、无描边；secondary=浅色实底（surface-sunken）、无描边；
         tertiary=纯文字、无底无描边；danger=文字或浅红底，不用红描边
图标按钮  三选一并写明：无容器纯图标 / 浅色实底圆 / 1dp 圆环（默认前两种）
输入框   1dp 描边（语义色）+ 实底
卡片     二选一：无描边+柔和阴影，或 1dp 装饰描边+无阴影（不要两者都上）
徽标/chip 可用胶囊形；普通按钮不得用胶囊形
状态     pressed/disabled 用底色变化表达，不靠描边变化
```

再写一条**描边预算**：一屏允许出现的描边元素只限输入框、卡片或分割线（二选一），
按钮/图标按钮/标签不得靠描边定义边界。验收时数一数每屏描边元素，超标即返工。

### 必须先有视觉参照，再写组件

文字章程只能定角色，定不了形面语言。开工前二选一：

1. 用户提供 1–3 张风格参照图（可以是其它品类的好产品），把"按钮/输入/卡片/
   图标按钮"四类组件的形面特征抄成规格（只抄形面逻辑，不抄品牌与资产）；
2. 渲染 2–3 个**风格 tile**（同一组按钮/卡片/输入框的三种形面方案）让用户选一个。

没有参照就开写，模型会退回"描边胶囊按钮 + 大圆角 + 全屏投影"这类通用默认样式。


## 1. 截图怎么收、怎么给

- **优先真机/模拟器截图**，商店五图只能当构图与卖点参考（营销合成图看不出真实状态）。
- 每个关键页面至少四态：默认、空、加载（骨架还是转圈要如实记录）、错误。
  有就再收：权限拒绝、键盘弹出、深色模式、小屏（320dp）。
- **全局组件的触发瞬间必须单独收**：每种 dialog、toast/snackbar、bottom sheet、
  下拉刷新、全局弹窗（如新消息弹窗）的现场照——这是统一组件契约的依据。
- 命名对齐页面 ID：`S03-filled.png`、`S03-empty.png`、`G-dialog-danger.png`
  （G- 前缀 = 全局组件）。存 `replica/screens/`，永不入包。
- 用户在会话里直接丢截图即可；agent 用读图能力逐张过，边看边填 §2 的文法表。

## 2. 文法提取（measure, don't guess，全记录进 components.md 附录）

对截图逐维度量，记录的是**体系**不是单个值：

| 维度 | 怎么量 | 记录成 |
| --- | --- | --- |
| 色彩角色 | 取色器数 bg/surface/border/text/muted/accent/danger 各角色；数灰阶有几个 | 角色表 + 灰阶档数（通常 5–7） |
| 字阶 | 字号/行高/字重，归到阶梯；只记字体类别不记字库 | 字阶表（size/line-height/weight） |
| 间距 | 量元素间隙，找基准（几乎总是 4 或 8 的倍数） | 间距档位表 |
| 圆角 | 数档位（通常 2–3 档：控件/卡片/全圆） | radius 档位表 |
| 阴影/高度 | 是投影体系还是描边体系；几档 | elevation 档位表 |
| 布局 | 列表行高、卡片内边距、导航高度、tab 结构 | 布局常量表 |
| 组件 | 每个重复 UI 部件的变体×状态×出现页面 | 组件盘点表（下节） |

## 3. 统一组件契约（本阶段最重要的产出）

原项目的通病是组件散装：每个 dialog 各写各的、Toast 直接系统调用（Kira 里
NewMessageDialog/ChargeVideoDialog/假来电弹窗互不相干）。新项目必须在写任何功能
页之前，把组件 kit 立起来。对每个组件写一节契约：

```
Dialog
  变体      confirm / danger / loading / custom-content
  结构      标题(可选) / 正文 / 操作区(主按钮+次按钮或纯文字)
  状态      常规 / 加载中(按钮转 spinner，标题正文保留) / 危险(主按钮=danger 色)
  tokens    宽度=spacing.screen-pad*2 封顶, 圆角=radius.lg, 背景=surface
  无障碍    焦点捕获、返回键=次按钮、 TalkBack 朗读标题+正文+按钮
  原场景映射  原项目所有 dialog 现场逐个列出 → 归入哪个变体
```

必立的契约清单：
- **Dialog**：上面的四变体；原项目每一个 dialog 现场（spec+截图）都要能归入某个变体，
  归不进去的要么加变体要么证明它该是独立组件。
- **Toast/Snackbar**：时长档位（短/长）、是否带图标、位置（底部/tab 上方）、
  暗底浅字还是 surface 底、与 dialog 的分工（toast=通知性，不可交互）。
- **BottomSheet**：拖拽条、高度档位（半屏/展开）、与 dialog 的分工（sheet=临时任务）。
- **Empty/Error/Loading**：空态（插画+一句话+下一步动作）、错误态（重试按钮）、
  加载态（骨架还是转圈，与原 App 行为对齐但视觉全新）。
- **Button/Input/ListRow/Card/Badge/Avatar**：变体（primary/secondary/ghost/danger）×
  状态（default/pressed/disabled/loading）全套。

## 4. 新体系设计（换骨：信息层级保留，表达全换）

逐维度做"刻意不同"决策，每条写 anti-reference：

| 决策点 | 换法举例 |
| --- | --- |
| 主色 | 换色相族（原橙 → 新青绿）；原主色进 sweep 黑名单 |
| 圆角/阴影策略 | 原大圆角+重投影 → 新细描边平面风；或反向 |
| 间距基准 | 原 4dp 基准 → 新 8dp 基准（密度变疏朗）；档位数可以不同 |
| 字阶 | 换阶梯数值与字重策略（原 500 主字重 → 新 600） |
| 构图 | 同页面同 job 换布局：原"头像左信息右"列表 → 新"头像上信息下"卡片网格（信息种类不减） |
| 动效 | 转场语言换（原右滑入 → 新淡入上移） |

然后把新体系写成 token（角色名通用，值全新）：

```json
{
  "colors":  {"bg": "#F7F7FA", "surface": "#FFFFFF", "text": "#1C1C22",
              "textMuted": "#6E6E7A", "accent": "#0B6F63", "onAccent": "#FFFFFF",
              "danger": "#C93838"},
  "spacing": {"xs": 4, "sm": 8, "md": 12, "lg": 16, "xl": 24, "screenPad": 16},
  "radius":  {"sm": 6, "lg": 14, "full": 999},
  "type":    {"body": [15, 22, 500], "title": [20, 26, 600], "caption": [12, 16, 400]},
  "pairs":   [{"name": "text on bg", "fg": "text", "bg": "bg", "level": "AA"},
              {"name": "onAccent", "fg": "onAccent", "bg": "accent", "level": "AA"}]
}
```

校验对比度：

```bash
python3 scripts/contrast.py replica/design/tokens.json   # AA 失败 exit 1
```

AA 底线：正文 4.5:1，大字/非文本控件 3:1。深色模式单独一套 colors 再跑一遍。

**常见不达标清单**（实战反复出现，立 token 时逐条过）：
- 占位符文字（placeholder）按正文要求 4.5:1——设计师常用的 40% 灰几乎全不达标；
  禁用态文字可豁免，但占位文字不行。
- 焦点环（focus ring）按非文本 3:1——浅色 ring 在浅画布上常只有 2.5:1；
- 输入框描边如果是唯一可识别依据，按 3:1——hairline 浅灰（tag 1.4:1）不行，
  要用中灰档；纯装饰分割线可放宽。
- 默认图标色按 3:1——装饰性图标可放宽，承载语义的图标不行。
- 白色文字压在亮强调色（橙/黄/青）上经常 2~3:1 不达标：要么用深色字压亮底，
  要么把强调色加深一档再配白字，要么强调色只做图标/徽标不承载文字。

## 5. 实现（Compose 为主，View 给路径）

- **Compose**：MaterialTheme 只借组件行为，颜色/字/形全走自研 token：
  一个 `DesignTheme`（`DesignColors`/`DesignShapes`/`DesignType` + `LocalSpacing`），
  `tokens.json` 是唯一真源（手抄一次成 `Tokens.kt`，或写生成脚本）。组件里**禁止
  裸写色值/px**——没这个纪律 token 体系就是摆设。
- ripple/indication 全局统一（换或关），edge-to-edge 与状态栏色一致性在主题层处理。
- **View 体系**（若换位矩阵选了 View）：styles.xml + theme overlay + Dialog 基类 +
  统一 Toast view，同样从 tokens 派生 dimens/colors。
- **View 体系实测坑**（toy 验证轮真实踩过，直接抄作业）：
  - Dialog 是独立窗口，子视图 elevation 阴影不渲染、`windowLightStatusBar` 不可靠——
    改用全屏 scrim 容器 + 软件层 `shadowLayer` 画柔和投影，并在 Dialog 窗口单独
    设置状态栏图标明暗；
  - API 35+ 强制 edge-to-edge 后，状态栏图标外观要在运行时按昼夜模式设置；
  - 按钮禁用态用 ColorStateList（背景/文字/描边三组），不要只改透明度；
  - M3 CircularProgressIndicator 的动画会周期性收缩成短弧，静态截图可能只剩残片——
    loading 组件用自绘完整圆环，保证任意帧可验收。
- 文案语调同时定：主按钮/空态/错误的措辞风格写三句"像谁不像谁"，组件契约里的
  默认文案按这个语调写（原 App 文案一个字不搬）。

## 6. Gallery 验收（先于任何功能页）

- debug-only 路由（如 `/design-gallery`）：全部组件 × 全部变体 × 全部状态一页陈列，
  深浅色各一份。
- 会话里有 android-dev/android-cli 就直接起模拟器截 gallery 存
  `replica/design/gallery/`；没有就给用户截屏清单。
- 验收标准（写进 components.md 末尾）：
  - [ ] 原项目每个 dialog/toast 现场都能映射到新契约某变体（附映射表）
  - [ ] contrast.py 零失败，深色模式也过
  - [ ] 并排对比：关键页面"信息层级同 job、构图/色彩/圆角/阴影/间距体系全部不同"
  - [ ] 组件无裸色值/裸 px（grep 十六进制色值只在 Tokens 文件出现）

**视觉验收必查的组件陷阱**（实战抓到过，结构自检发现不了）：
- dialog 声称"双操作"但只渲染出一个（主操作按钮漏加/被遮挡/白底白字）——
  必须同时看到两个操作，危险弹窗的主操作是 danger 色；
- disabled 态与 enabled 态视觉无差异（同一色值）——禁用态必须有可辨样式；
- 阴影渲染成硬边灰色矩形/色块而不是柔和投影——检查 elevation 与背景层；
- 状态栏图标明暗与页面主题不匹配（浅底白字不可读）——按主题设置图标外观；
- loading 对话框内容未居中、spinner 只剩一个残片——动画与布局都要截图确认。
- **Insets 必须按状态栏 inset 高度核对**：edge-to-edge 下元素 y=0 合法，元素树
  坐标看不出重叠；要对比标题/返回键起始 y 与状态栏高度，并目检截图里标题是否与
  时间/信号同层像素重叠。抽查 Tab 主页/列表/详情/二级页/弹窗——一页漏 inset 即缺陷。
- **服务端内容里的旧品牌**：官方账号名/欢迎语/系统消息出现原 App 名 = 品牌泄漏
  （即使文案来自服务端）；服务端改名，或客户端显示层兜底映射。
- **格式化占位符泄漏**：UI 文案出现 `%d`/`%s`/`{0}` 即缺陷；服务端下发的权益文案
  必须格式化或校验后才上屏。
- **跨截图一致性**：tab 项数、头部 insets、同一组件形面在不同截图间必须一致；
  单张通过 ≠ 全局一致。

**系统级风格审查（逐组件验收之外，必须把 gallery 当一套看）**：
- 数每屏描边元素：按钮/图标按钮不应靠描边定义边界；一屏出现"所有次级按钮都是
  描边胶囊""所有图标按钮都是圆环"即驳回（典型 AI 默认样式）；
- 胶囊形只允许徽标/chip，普通按钮用章程规定的圆角矩形；
- 同类组件跨页面必须同形：不能一页实底、一页描边、一页投影；
- 站在普通用户视角看整屏：它像"一个正常产品"，还是像"一组示例控件"。

Gallery 通过后，rebuild 的功能切片才开工：切片只准用组件 kit 拼页面，缺组件回本阶段补契约。

## 7. 视觉验证铁律（反面案例教训，违反=切片不通过）

一次无 skill 的复刻在这里全灭：AI 用"UI 元素树里有文字"证明页面正常，实际上每个
页面视觉空白、风格简陋到无法上架；截图工具返回的图片它自己看不了，就默默跳过了
截图验证。由此立铁律：

1. **元素树不等于视觉**。`ui_describe`/uiautomator 的文字清单只能证明"节点存在"，
   不能证明"页面好看、不空白、排版正确"。视觉验收只有一种证据：**截图 + 看图**。
2. **看不了图就换路，不许跳过**。当前模型不支持图像输入时：用截图给用户看 +
   明说"我无法亲自看图，以下结论基于结构树，需要你目检"；绝不允许"我看不了所以
   假装验证过了"。装了有图像输入能力的模型/会话再亲自复看一遍。
3. **"页面看起来正常"必须是截图结论**，交付汇报里"全部跑通无崩溃"前面必须加
   "视觉验收（截图 N 张，见 replica/shots/）"或"结构验收（未视觉确认）"——
   两者不得混淆陈述。
4. **截图要真的在目标 App 里**。反面案例里"Me Tab 验证"截到的是系统桌面
   （文字列表里混着 Calendar/Chrome/Gmail 都没发现）。每张验收截图先检查包名/
   前台 Activity 是不是目标 App，再谈页面内容。
5. **占位文案 = 未完成**。"Coming soon" 这类占位 Tab 在 v1 里要么不做进导航，
   要么在 features.csv 里如实标 no 并在交付汇报里点名，不许当成"跑通了"。
