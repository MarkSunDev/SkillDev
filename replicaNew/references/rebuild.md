# 阶段 4–5：scaffold 立骨 + rebuild 重写

## 阶段 4：scaffold（新工程骨架）

- **全新仓库**：新 git init、新 remote、初始提交不携带任何原项目历史（原项目的历史
  = 作者邮箱 + 提交习惯 + 文件重命名轨迹，全是关联证据）。
- **新包名**：applicationId 与 namespace 全新，且不要是原包名的"变体"（原
  `com.a.b` 新 `com.a.c` 就是变体）。模块的 namespace 组织方式也换（原按层，新可按特性）。
- **骨架按 blueprint 的换位矩阵生成**：模块数、目录树形状、DI 初始化方式都来自换位
  决策，不是原项目的镜像。写一个最小的可编译可安装的空壳（Application + MainActivity
  + 占位 tab），先把构建/CI/签名流程跑通。
- **构建脚本从零写**：build.gradle、proguard 规则、CI 配置不要从原项目拷——
  456 行的 proguard 迁移注释就是 buzzme 抓到 naya 痕迹的地方。混淆规则按新项目
  实际用到的类重新积累。
- 原则：**骨架阶段就跑一次 simcheck**（对空壳），确认起点为零。

## 配置集中化（骨架期就立好，后面所有切片只准引用）

所有"会因换主体而变"的值**只允许出现在一个地方**，散落在代码里的 key 是后期换包
最大的成本（也是家族项目互相漏配置的根源）：

- 一份 `app-config.json`（或等价的单一 gradle.properties 段）集中管理：API/TCP
  host（prod/dev）、各 SDK 的 appid/appKey（腾讯 IM、Firebase、BytePlus、AppsFlyer…）、
  google-services.json 的按变体路径、订阅 SKU 前缀与金币 SKU 前缀（服务端下发为
  默认，但客户端做 `startsWith` 判断的前缀必须进配置）、客服邮箱模板、法务页域名，
  以及**服务端可能做白名单的 `app_name`（它是通网开关，不是品牌字段——见
  diverge §4 探针矩阵）**。模板见 `templates/app-config.example.json`。
- 构建期把配置注入 BuildConfig（或运行时读入 AppConfig 对象），**业务代码只准
  引用 AppConfig 常量**，出现裸域名/裸 appid 字符串即为缺陷。
- 真值不入库：仓库里只有 `app-config.example.json`（占位值），真值走
  `app-config.local.json`（gitignore）或 CI secret。rebind 阶段换主体 = 改这一个
  文件 + 换 keystore，其余零改动。
- google-services.json 是 Google 强制的按变体文件，无法合并进单一配置，但它的
  **路径**要登记进 app-config 的 manifest 清单，audit 时核对路径指向新 Firebase 工程。
- mock/演示数据同理：demo 开关、假余额、演示会话全部挂 AppConfig 的 debug 变体，
  release 构建物理上取不到这些值。

## 阶段 5：rebuild（按规格重写）

### 信息流纪律

写代码时桌上只有四样东西：`replica/spec.md`、`replica/blueprint.md`、
`replica/design/`（token + 组件契约）、`replica/features.csv`。遇到 spec 没写清的行为：

1. 回原项目**只读**确认该行为；
2. 把结论补进 spec（用产品语言，不抄实现）；
3. 合上原项目，按 spec 实现。

禁止开着原项目的文件"照着写"。逐行翻译是本阶段唯一的致命错误——改名换皮式的
翻译产物在 token 级和结构级都会被 simcheck 抓出来。

### 建造顺序（垂直切片；每阶段有独立验收，不许水平铺量）

0. **契约先行**：spec/blueprint/design 三件套齐了才动代码。
1. **壳 + 会话**：主目的地导航骨架、登录/刷新/登出/注销边界、安全会话存储
   （按端点+账号作用域）、无密钥进源码/日志/错误文案。
   验收：真实账号能进壳、请求进行中可导航、重启不丢会话、过期会话可恢复。
2. **真实读面**：资料 → 发现/筛选 → Feed/分页 → 喜欢/访客 → 详情 → 钱包/目录。
   每页五态齐全；样例内容显式标注。
   验收：每个读都到真实服务、刷新保留已加载窗口、有截图或契约证据。
3. **核心写**：滑动（三种语义独立）→ 点赞/回读 → 资料编辑/头像 → 拉黑/举报 →
   发帖/删帖。每切片要：稳定意图标识（重试同键）、请求前校验、可见 pending、
   权威回读、明确失败文案、QA 数据清理。
4. **聊天与媒体**：仅在用户态传输通道存在时启用；草稿+幂等键、附件校验/重编码/重传、
   提交态渲染、已读游标、拉黑后的不可用行为。
5. **商业/通知/通话**：金币/会员/礼物/通知/通话/设置——每项都必须由真实能力标记
   门控。**大厅可见不等于可购买，设备注册不等于推送可达，钱包扣费不等于礼物送达。**
6. **加固**：故障注入（清单见 audit 门禁二）+ 无障碍 + 依赖审计。
7. **发布证据**：debug/release 构建、测试结果、真实探针输出、owned QA 写证据、
   装机截图、状态账本（connected/partial/blocked/deferred）、可复现命令。

should/could 功能随后；明确不做的（spec §8）不做。
`replica/build-log.md` 每切片一行，进度、缺口、意外如实记。

### 传输与并发不变式（架构契约，与 UI 框架无关）

- **成功判定按操作各自规则**：不是所有接口都用同一个 `code=Success`（实战案例：
  某接口 `code=0` 表示成功，被误判为失败）；客户端只认该操作文档化的规则。
- 非 2xx / 重定向 / 错误 content-type / 超大体 / 畸形包体 / 过期会话响应一律视为失败。
- 传输层关自动重定向与自动重试；重试只在意图层、用同一个 request identity。
- 会话快照按"端点 + 代次"作用域：飞行中响应到达时若端点/账号已变，**丢弃而不是显示**。
- 刷新时保留已加载内容；后台轮询失败不清空用户可见数据；最新的显式 tab/路由意图获胜。
- 归一化只做一次（可选字段显式 null/空），不许每个页面各自兜底；未知字段不许崩页。

### 相似度消除的实操手法

- **命名体系先定后写**：blueprint 定好新前缀/后缀语义（组件、工具、层），写代码时
  自然长出新体系，而不是写完再全局重命名。
- **注释语言与风格**：与原项目相反（原中文论文式 → 新英文短句式，或反之）。绝不写
  "照抄自 XX""对齐 XX 项目"这类出处注释——这是家族指纹的头号来源。
- **工具类零复用**：加密、时间、扩展函数、对话框基类……每个工具在新项目里按需求
  重新写。原项目的 `Mmkv.kt`/`DeviceIdentity.kt` 这类高频复用文件是相似度重灾区。
- **代码组织惯性自觉**：同一个作者的重写倾向于产出相同的函数分解。对策：让切片的
  实现顺序打乱（先写 UI 契约还是先写数据层，与原项目相反）、类型分解数量刻意不同
  （原 1 个 3783 行的 MeScreen，新就拆成多文件；原拆成 7 个类的，新合成 2 个）。
- **资源命名**：drawable/string/layout 的命名规则换一套（原 `ic_tab_chats` →
  新 `menu_chats_icon`），颜色进 token 不写裸值。
- **每完成 2–3 个切片跑一次 simcheck**，containment 或文件对超标就当场返工——
  积累到后期再返工成本翻倍。

### 与原项目"必须相同"的部分怎么处理

- 协议语义（保留后端时）：DTO 的字段号/字段名是契约，生成的 protobuf 类必然长得
  像。处理法：生成代码整目录标记为"契约产物"（文件头注明），审计时把生成目录加入
  simcheck 的豁免并单独说明；客户端侧的注册表/编解码封装自己写。
- 业务数值：直接按 spec 写，加测试钉住。数值相同不是相似度，是正确性。

### UI 用组件 kit 拼，不许现场造组件

功能切片只准用 design 阶段组件契约里的组件拼页面；发现缺组件（某变体/状态契约没覆盖）
就回 design 阶段补契约、补进 gallery，再回来用。切片里出现自造 dialog/toast 是
返工信号——那正是原项目"组件散装"的通病，别把它一起复刻了。

### 支付链路（社交 App 必踩，实战核对过）

- **商品 ID 以服务端下发为准**，商店后台必须逐条对齐：实测踩坑——服务端下发
  `kira_coins_a` / `premium_yearly` 这类 ID，客户端配置里的占位 `toy_*` 会让
  Play 购买直接失败。开工前导出一份"服务端商品 ID ↔ Play Console 商品 ID"对照表。
- **dev 测试计费 = 真实后端接口 + 伪 purchaseToken**（仅 debug 源集），不是客户端
  假数据；release 只保留商店 Billing。客户端永不本地发放权益，一切以服务端验单为准。
- Billing 连接按需幂等（不要指望 Activity 启动时连一次就够）；连接成功后查询未核销
  订单重走验单（补单）；购买/订阅/补单后调用用户余额接口刷新本地显示。
- 订阅赠送金币等权益的到账时机由服务端决定——客户端只认服务端 Success，不自行推算。

### 每个切片的完成定义（沿用 social-app-delivery 的证据标准）

- [ ] 正常路径可走通，结果来自真实数据源（不造假数据）
- [ ] loading/ready/empty/error/unavailable/pending 状态齐全，不拿占位数据冒充成功
- [ ] 写操作幂等或去重（防双击双发）
- [ ] 401/过期会话行为正确（登出或刷新，不串号）
- [ ] **视觉验收**：切片每个页面截图存证（`replica/shots/`），且截图时核对前台
      Activity/包名确实是本 App 本页面；结论分"视觉验收（看过图）"和"结构验收
      （只看过元素树）"两档，交付汇报必须注明是哪档——元素树有文字 ≠ 页面不空白
- [ ] **mock 显式**：一切假数据/演示模式只在 debug 变体且 UI 上有可见标识；
      后端故障降级走显式 unavailable 状态，禁止静默切假数据宣布成功
- [ ] 真实交互路径走过一遍：键盘弹出时的点击目标、列表滚动中的防抖、双击返回键
- [ ] features.csv 与 build-log 更新
- [ ] 该切片涉及的新文件跑过 simcheck
