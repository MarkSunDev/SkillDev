# 阶段 2：diverge 立异（差异化设计）

目标：在写一行代码之前，把"新 App 和原 App 怎么不同"定义成可执行的决策。产出
`replica/blueprint.md`。这个阶段的质量决定 audit 阶段能不能过——差异化是设计出来的，
不是重写时顺手做出来的。

## 1. 新身份（三件套同时定）

- **产品名与一句话定位**：不与原 App 名字/品类头部的竞品相似（商标检索：USPTO/EUIPO/
  WIPO + 商店搜索 + 域名）。定位角度最好有真实差异（人群、场景、玩法侧重）——
  "又一个同款"在商店重复内容政策下本身就是风险。
- **视觉方向**：配色族换掉（原是橙系就别选邻近橙）、字体角色、构图密度、动效语言。
  写成 token 角色（bg/surface/text/accent/danger...）而不是像素值。图标/插画全部新做。
  本阶段只定方向；截图输入→文法提取→token 体系→统一组件契约的完整流程在
  references/design-system.md（design 立形阶段）。
- **运营身份**：新域名族、新客服邮箱拼法（不要沿用 plus-addressing 家族模板）、
  新法务页——见 references/disassociate.md。

## 2. 契约/表达边界表（blueprint 的核心）

区分"必须保持一致的契约"与"必须重做的表达"。这张表是后面所有决策的仲裁依据：

| 层 | 契约（保持） | 表达（重做） |
| --- | --- | --- |
| 功能 | 功能矩阵 must 行的行为、业务规则数值 | 页面结构、交互手势、信息层级 |
| 网络 | 协议语义（若保留后端：字段/错误码/命令语义） | 端点命名（若新后端）、DTO 分解方式、拦截器结构 |
| 数据 | 实体关系、状态机 | 字段命名、存储选型、schema 划分 |
| UI | 无（UI 层没有契约，全部重做） | 组件体系、导航体系、主题、资产 |

判断口诀：**用户或服务器需要依赖的才是契约；代码怎么组织全是表达。**

## 3. 换位矩阵（每行一个"刻意不同"）

对原项目的每个关键技术决策，选择一个**有真实理由的**不同方案，写进 blueprint：

| 决策点 | 原项目（示例） | 新项目 | 理由 |
| --- | --- | --- | --- |
| UI 框架 | Compose | View 体系 / 双轨 | 结构指纹差异最大 |
| 架构模式 | MVI + 单 VM 四态 | MVVM + 多状态流 / 状态机库 | 状态指纹差异 |
| 导航 | 自研覆盖层栈 | Navigation-NavHost / 单 VM 路由 | 文件树形状不同 |
| DI | Koin | Hilt / 手写 ServiceLocator | 初始化代码形态不同 |
| 网络 | Retrofit+PbConverter | Ktor / OkHttp 原生 + kotlinx.serialization | 网络层文件结构不同 |
| 存储 | MMKV+Keystore | DataStore+EncryptedFile | 工具类指纹不同 |
| 模块划分 | layer 三层 27 模块 | 按 feature 垂直切 / 单 module+包约束 | 目录树是第一眼相似度 |
| IM/通话 | 腾讯 TXIM/TUICall | 其他供应商（或同供应商不同实现封装） | 见 §5 例外规则 |
| 命名语言 | 中文注释+Buzz 前缀 | 英文注释+全新前缀体系 | 注释是最强指纹 |

规则：每行都必须有"真实理由"栏；"为了不像"不是理由本身，要落到工程属性
（团队熟悉度、库维护状态、招聘市场、性能特征）。换位不是目的，**自然差异才是**——
两个独立团队本就不会做出相同选择。

## 4. 协议策略（先定，影响一切）

新 App 是**接原后端**还是**连后端一起独立**？两种走法的契约边界完全不同：

- **保留原后端**（快，适合验证市场）：协议层（proto 字段/命令号/错误码/misc 键名）
  全部属于契约，照 spec 对齐；但**客户端的协议实现代码要自己写**（编解码、注册表、
  拦截器），且 proto submodule/生成代码的组织方式要换（原是 git submodule+Python 生成，
  新的就用本地 proto 源+Gradle 插件，或直接 vendor 生成物换个包名）。
  服务端 misc 键名、设备 ID 前缀这类"服务端读的键"按服务端要求保持，其余请求头字段
  名可以服务端配合改。**注意：接同一后端意味着数据面天然关联，账号体系若要隔离
  需服务端侧分区，这个决定要在 blueprint 里明示给用户。**
- **新后端**（彻底独立，工作量大数倍）：API 契约重新设计（只保留业务语义，命名风格
  换新——REST 资源化 vs 原来的命令式），新域名新部署。此时 simcheck 的网络层豁免
  全部失效，客户端可以做到对原项目零结构相似。

### v1 场景的默认选择（核心玩法验证 + 买量测试）

第一版只做核心玩法验证和买量测试时，**默认走"保留原后端"**：

- 服务端现有接口、请求/返回格式（protoId、字段、错误码、misc 键名）**按契约 1:1
  保持**，客户端网络层重新封装（自己写编解码/注册表/拦截器，proto 生成目录标记
  "契约产物"并写入 simcheck 豁免说明）；
- 此时差异化火力全部集中在客户端表达层（架构换位 + design.md 视觉体系）；
- 买量数据说话之后，再决定是否投入"新后端"的彻底独立路线。

### 开工前后端预检：身份探针矩阵（必做，10 分钟）

不只探"后端活没活"，还要探"后端认不认你"。对登录接口用 curl 跑一张矩阵，每个
字段单独变化、其余固定，记录状态码：

| 变量 | 测试值 |
| --- | --- |
| app_name（请求头 params 里） | 原 App 的 app_name / 新 App 名 / 空 |
| package_name | 原包名 / 新包名 |
| device_id 格式 | 原 App 格式（uuid/哈希/前缀）/ 新前缀 / 长度变化 |
| locale | en_US / zh_CN |
| 连续请求 | 连发 5 次看是否限流（403 也可能是 WAF 限流，别误判成白名单） |

真实案例（toy 复刻 Kira）：逐一排除后定位到**服务端对 app_name 做白名单**——只有
`kira_android` 返回 200，`toy_android` 无论 package_name 是什么都 403；包名、
device_id 格式都不是开关，locale 也不是。结论写进 blueprint 的契约表并让用户拍板：

- **沿用原 app_name 才能通网**（v1 验证市场的常用选择）——意味着服务端把新客户端
  视为原 App，数据面天然关联，必须在 blueprint/rebind.md 明示；
- **要求服务端把新 app_name 加进白名单**（彻底独立的正路，需服务端配合）。

预检还包含：后端是否活着、协议口径是否变了、TLS/证书是否正常。**不许静默切 mock
假装成功**——预检不过就在 blueprint 里写明降级策略（显式 unavailable 或换环境）。

## 5. 哪些"相同"是可接受的

- 三方 SDK 相同（都用 Play Billing、都用某 IM SDK）：供应商就那几家，属于行业共性。
  但 SDKAppID 必须是**新项目自己的账号**（见 disassociate），封装层代码要重写。
- 平台惯用法相同（Compose 的 `remember {}`、协程 `viewModelScope`）：语言/框架级
  惯用法无指纹价值，simcheck 阈值已容忍。
- 业务数值相同（配额、计费周期、年龄范围）：这是契约，本来就该相同。

## 6. blueprint.md 的验收自检

- [ ] 换位矩阵 ≥ 6 行且各有真实理由
- [ ] 契约/表达边界表覆盖功能、网络、数据、UI 四层
- [ ] 协议策略已与用户确认并写明
- [ ] 新名字过了商标/商店/域名检索（或标注待查）
- [ ] 视觉方向有 anti-reference（"长得像谁就不行"写出来）
- [ ] 产品有至少一个原 App 没有的真实差异点（不是换个皮肤）
